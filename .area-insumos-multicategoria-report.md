Fecha: 2026-10-30

## 1. Schema / migración

Archivo nuevo: `database/mysql/migraciones/2026-10-30-producto-categorias-multiples.sql`

```sql
CREATE TABLE producto_categorias (
  producto_id  CHAR(36) NOT NULL,
  categoria_id INT NOT NULL,
  PRIMARY KEY (producto_id, categoria_id),
  FOREIGN KEY (producto_id) REFERENCES productos(id) ON DELETE CASCADE,
  FOREIGN KEY (categoria_id) REFERENCES categorias_producto(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_as_cs;

INSERT INTO producto_categorias (producto_id, categoria_id)
SELECT id, categoria_id FROM productos WHERE categoria_id IS NOT NULL AND ecommerce_item_key IS NOT NULL;

(el `AND ecommerce_item_key IS NOT NULL` se agregó en un commit de seguimiento — ver sección 8, concern #2, ahora corregido.)

Aplicada directamente contra la base local (`mysql -h127.0.0.1 -P3306 -uroot -p1429 sistemapos < database/mysql/migraciones/2026-10-30-producto-categorias-multiples.sql`) — corrió sin errores.

Confirmación del backfill en local (primera versión, antes del fix de seguimiento):

```
(coincide exacto: los 5 productos que ya tenían `categoria_id` quedaron con su fila inicial en `producto_categorias`).

**Corrección de seguimiento**: los 5 productos backfillados en local resultaron ser TODOS de alta manual (`ecommerce_item_key IS NULL` — en local todavía no hay productos sincronizados del e-commerce con categoría). `database/mysql/schema.sql` se actualizó agregando el `CREATE TABLE producto_categorias` completo justo después de `productos` (antes de `inventario_productos`), siguiendo la misma convención que `pedido_areas` (tabla agregada después pero plegada en el `schema.sql` como `CREATE TABLE` completo junto a sus tablas relacionadas, no como `ALTER` al final del archivo).

**Nota para quien despliegue a producción**: el archivo de migración queda listo en `database/mysql/migraciones/` pero NO se corrió contra producción — eso le corresponde al usuario, igual que las migraciones anteriores de este proyecto.

## 2. Contrato de sincronización (`tipos.ts` + validación)

- `backend/src/modules/integracion_ecommerce/tipos.ts`: se agregó `categories?: string[]` a `SnapshotProducto`, documentado como "nombre + ancestros, ya expandido allá", opcional por los avisos en vuelo.
- `backend/src/modules/integracion_ecommerce/integracion_ecommerce.routes.ts`: el `eventoSchema` (zod) para `PRODUCT_SNAPSHOT` NO tenía `categories` — como los `z.object()` de zod descartan claves no declaradas, sin este cambio el campo se habría perdido silenciosamente al validar el body HTTP. Se agregó `categories: z.array(z.string()).optional()` al payload. **Esto no estaba explícito en el encargo pero es necesario para que el contrato funcione de punta a punta vía HTTP** — lo marco como la única desviación real del brief (una adición necesaria, no un rediseño del contrato).

## 3. `recepcion.ts`

- `aplicarSnapshot()` ahora resuelve `nombresCategorias = snap.categories?.length ? snap.categories : (snap.category ? [snap.category] : [])`.
- Nuevo helper plural `obtenerOCrearCategorias()` (llama al singular existente por cada nombre, deduplicando ids, preservando orden de aparición) — no se reescribió el singular, se agregó un hermano plural como permitía el brief.
- `productos.categoria_id` sigue fijándose a `categoriaIds[0] ?? null` (la primera resuelta), igual que el comportamiento "whichever is first" de siempre — ahora puramente informativo/legacy.
- Se refactorizó el loop de ítems para capturar `productoId` tanto en el branch de INSERT como en el de UPDATE, y después de cada ítem se llama a `reemplazarCategoriasProducto(client, productoId, categoriaIds)`: `DELETE FROM producto_categorias WHERE producto_id = $1` + un `INSERT` por cada id — idempotente, dentro de la MISMA transacción de `aplicarEvento` (no abre `BEGIN`/`COMMIT` propio).

## 4. `area_defecto` — forma final (`con_sentido.repository.ts::SELECT_PRODUCTO`)

```sql
SELECT p.id, p.nombre, p.sku, p.precio, p.descripcion, p.imagen_url, p.activo,
       p.precio_mayorista, p.mayorista_desde, p.nota_mayorista,
       COALESCE(p.ecommerce_product_id, p.id) AS grupo,
       p.ecommerce_publicado, (p.ecommerce_item_key IS NOT NULL) AS sincronizado,
       cp.nombre AS categoria,
       (SELECT GROUP_CONCAT(DISTINCT nombre ORDER BY nombre SEPARATOR ', ')
          FROM (
            SELECT cp.nombre AS nombre
            UNION
            SELECT cpt.nombre AS nombre
              FROM producto_categorias pct
              JOIN categorias_producto cpt ON cpt.id = pct.categoria_id
             WHERE pct.producto_id = p.id
          ) todas_categorias
       ) AS categorias,
       COALESCE(ip.cantidad_actual, 0) AS stock,
       CASE WHEN
         EXISTS (
           SELECT 1 FROM categorias_producto cpi
           LEFT JOIN modulos mi ON mi.id = cpi.modulo_id
           WHERE cpi.id = p.categoria_id AND mi.slug = 'insumos'
         )
         OR EXISTS (
           SELECT 1 FROM producto_categorias pci
           JOIN categorias_producto cpj ON cpj.id = pci.categoria_id
           JOIN modulos mj ON mj.id = cpj.modulo_id
           WHERE pci.producto_id = p.id AND mj.slug = 'insumos'
         )
       THEN 'insumos' ELSE 'con_sentido' END AS area_defecto
  FROM productos p
  LEFT JOIN categorias_producto cp ON cp.id = p.categoria_id
  LEFT JOIN inventario_productos ip ON ip.producto_id = p.id
```

Se quitó el `LEFT JOIN modulos m2 ON m2.id = cp.modulo_id` porque ya no se usa en ningún lado (la lógica vieja `CASE WHEN m2.slug = 'insumos'` se reemplazó por los dos `EXISTS`).

El campo nuevo `categorias` usa el mismo criterio de unión que `area_defecto`: la categoría de `categoria_id` UNIDA con todo lo que haya en `producto_categorias`, sin duplicados (`UNION` + `GROUP_CONCAT(DISTINCT ...)`).

## 7. Desviaciones del brief

1. **Zod schema en `integracion_ecommerce.routes.ts`**: el brief no lo mencionó explícitamente, pero sin agregar `categories` al `eventoSchema` de zod, el campo se habría descartado silenciosamente en cualquier request HTTP real (zod descarta claves no declaradas por defecto). Se agregó `categories: z.array(z.string()).optional()`. Esto es una extensión necesaria del mismo contrato, no un cambio de diseño.
2. **Verificación vía función directa, no HTTP**: se verificó llamando `aplicarEvento()` directamente (mismo código que usa `POST /ecommerce/eventos`) en vez de por HTTP con `curl`, porque exige configurar `ECOMMERCE_SYNC_URL`/`ECOMMERCE_SYNC_KEY` y no tenía permiso para leer el `.env` del backend (contiene credenciales). El código de negocio ejercitado es exactamente el mismo (`aplicarEvento` → `aplicarSnapshot`); solo se evitó la capa HTTP + autenticación por motivos de permisos, no de diseño.
3. Todo lo demás se implementó tal como se especificó.

## 8. Preocupaciones para quien despliegue / para el lado e-commerce

1. **Migración en producción**: el archivo de migración queda pendiente de correr en producción. Es puramente aditiva (nueva tabla + 1 `INSERT ... SELECT` de backfill), segura de correr directo, sin paso destructivo.
2. **[CORREGIDO] Filas obsoletas (`stale`) en `producto_categorias` para productos de alta manual editados después del backfill**:
   - Hallazgo original: el backfill de la migración le creaba una fila en `producto_categorias` a TODOS los productos que ya tenían `categoria_id`, incluyendo los de alta manual (Con Sentido, no sincronizados). Como `crearProducto`/`editarProducto` nunca tocan `producto_categorias`, si alguien editaba la categoría de un producto manual backfillado, la fila vieja quedaba apuntando a la categoría ANTERIOR, y por el OR en `area_defecto` el producto podía quedar pegado en "insumos" aunque se le hubiera cambiado a una categoría no-insumos. Lo reproduje explícitamente y confirmé el bug (`areaDefecto: 'insumos'` después de editar a una categoría no-insumos).
   - **Corregido** en el commit de seguimiento `8fa1fd2` ("fix(con-sentido): el backfill de producto_categorias no incluye productos manuales"): el backfill de la migración ahora excluye productos manuales con `AND ecommerce_item_key IS NOT NULL`, porque esos productos nunca necesitan fila en `producto_categorias` — `area_defecto` ya los resuelve directo por `categoria_id`, y `crearProducto`/`editarProducto` jamás leen ni escriben la tabla N:M.
   - Base local corregida a mano para igualar lo que la migración ya corregida habría hecho: `DELETE pc FROM producto_categorias pc JOIN productos p ON p.id = pc.producto_id WHERE p.ecommerce_item_key IS NULL;` → **5 filas borradas** (los 5 productos backfillados en local eran TODOS manuales, ya que local todavía no tiene productos sincronizados del e-commerce con categoría) → `producto_categorias` quedó en 0 filas.
   - Reverificado el escenario exacto que reproducía el bug (alta manual con categoría insumos, editado a una categoría no-insumos): ahora `producto_categorias` tiene 0 filas para ese producto tanto antes como después de editar, y `areaDefecto` pasa correctamente a `con_sentido` sin quedar pegado. También se reconfirmaron, sin cambios de resultado, el escenario de sincronización A/B/C (multi-categoría insumos / multi-categoría sin insumos / fallback a `category` singular) y el alta manual crear+editar simple.
   - `crearProducto`/`editarProducto` NO se tocaron — el fix es enteramente en la migración/backfill, como se pidió.
3. **Orden de `categories` no garantizado**: `productos.categoria_id` queda en la primera categoría de la lista que mande el e-commerce, que puede variar de un snapshot a otro si el e-commerce no garantiza el orden. Esto es puramente informativo ahora (ya no decide el área), pero si algún reporte o pantalla vieja lee `categoria`/`categoria_id` esperando estabilidad, podría "saltar" entre reenvíos. No se detectó ningún consumidor que dependa de que sea estable más allá de mostrarlo.
4. **Contrato del e-commerce**: no se tocó el repo del e-commerce. Lo único asumido del contrato (según el brief) es que `categories[]` ya viene con nombres de categoría expandidos con ancestros, deduplicados, sin garantía de orden — eso es exactamente lo que este lado consume.
